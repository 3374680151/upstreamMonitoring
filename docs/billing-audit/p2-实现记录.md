## 4. 自测结果（真实库）

- 迁移幂等执行，`sites.quota_per_unit` / `admin_sites.quota_per_unit` 列就位；
- 手动 `runBillingAuditOnce`：inserted=25、checked=325、**mismatch=8**（此前 0 红）；
- 红色样例：gemini-2.5-flash 主站收用户 $0.000026（group_ratio=1.0），上游「反重力Gemini」分组实付 $0.00000231（rate 0.1）→ 约 11 倍差价，`main_billing_inconsistent + group_ratio_gap`；
- 证据快照已脱敏（无 `api_key.key`、无用户邮箱）；
- 注意：正式 8000 实例是旧代码，仍会把 sub2api 上游行判成 `no_log_api`；灰行重判会在新进程接管后自动翻案（1 小时冷却）。

## 5. 已知边界

- sub2api usage 只能回看 ~500×6 条（时间倒序），更久远的灰行等新请求落库后靠重判翻案；
- 官方价同步只回放**最近一次主站同步成功**的快照，主站长期没同步则价格也停更（日志会打印 `[官方价同步]`）；
- 告警只在「本轮新增红行」时发，历史红行不重复轰炸；单轮上限 8 条明细。

## 6. 追加修复（2026-09-09）：GPT 行 no_upstream_log——上游重建库后日志 id 重新计数

**现象**：gpt-5.6-sol（上游 gopay / api.lukyface.com，NewAPI 平台）全部灰 `no_upstream_log`，但上游 `/api/log/self` 实测可用且能精确找到同一条请求。

**根因**：gopay 上游重建过日志库，日志 id 从 1 重新计数（total=1893、最新一条 id=1）。跨轮去重按**裸 upstream_log_id** 判重（且不分上游站点），历史行占用的 id 1/3/5 与新日志的 id 1/3/5 撞车，匹配环节把新日志全部误杀。

**修复**（三层）：

1. `billing_request_checks` 新列 `upstream_log_created_at`（schema.py `BILLING_CHECK_COLUMN_ADDITIONS`，init_db 自动 ALTER）——匹配成功时落上游日志自身时间；
2. 跨轮判重改为「上游站点 + log id + 参考时间（±匹配窗）」三要素（`_upstreamLogAlreadyUsed`）：同 id 但时间相差天级的新日志不再被误杀；历史行没有新列时退回用主站 request_at 近似比较；时间解析失败的占用条目保守按命中处理；
3. 重判池纳入 `unmatched` 行（24h 硬限界）：上游日志拉取瞬时失败、或 id 重计数历史误判的灰行，24 小时内每轮按 checked_at 最老优先翻案重审。

**验证**：行 1941 单行直跑翻案成功——匹配上游日志 id=5，且抓出真问题：上游日志自记分组倍率 0.06 vs 监控快照公示 0.08（`upstream_ratio_drift`），主站收 $0.0242 vs 上游实付 $0.0121。第二轮核对确认占用链自洽（同 id 新日志持续可配，已配对不重复消费）。
