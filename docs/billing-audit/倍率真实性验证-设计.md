**实际扣的钱按显示价算分毫不差 → 绿「正常」；显示的和实际收的对不上 → 红

## 计费原理（来自上游真实源码 computeTokenBreakdown）

上游（sub2api / NewAPI 同构）计费分两层：

```
列价成本 = 输入tokens×输入单价 + 输出tokens×输出单价
         + 缓存读tokens×缓存读单价 + 缓存写tokens×缓存写单价
实际扣的钱 = 列价成本 × 分组倍率
```

* 「加权」来自四类 token **单价本身不同**（如 官方 gpt-5.6-sol：输入 $4、
  缓存读 $0.4=一折、缓存写 $5、输出 $20 / 1M tokens），不存在额外加权系数；
* 单价之上还有服务档位 / 长上下文 / 时段等合法调整层（这些都是**明示**的），
  与「暗改」无关——暗改指：显示的价卡/倍率与实际收的钱对不上。

## 两个验证（对应两种暗改）

### 验证一：分组倍率有没有被暗改

```
真实分组倍率 = 实际扣的钱 ÷ 列价成本
显示分组倍率 = 上游公示/日志自记的分组倍率

真实 ≈ 显示 → 绿「正常」
真实 > 显示 → 红「暗改倍率」（偷偷涨分组倍率，多收钱）
真实 < 显示 → 绿（给得便宜，多挣）
```

真实数据：

| 渠道 | 列价成本 | 实际扣的钱 | 真实分组倍率 | 显示分组倍率 | 结论 |
|------|---------|-----------|------------|------------|------|
| gopay 1941 | $0.20199 | $0.01212 | ×0.0600 | ×0.06 | 🟢 分毫不差 |
| text168 201 | $0.005075 | $0.000609 | ×0.1200 | ×0.12 | 🟢 分毫不差 |

上游若把显示 0.06 实际按 0.1 收 → 真实 ×0.1 vs 显示 ×0.06 → 红。

### 验证二：模型价格有没有被暗改

列价成本由上游价卡决定。比对**两个时点的上游价卡**（监控模块每轮已抓
`/api/pricing` / `groups/rates`，快照现成）：

```
本轮上游价卡（model_ratio / completion_ratio / 缓存折扣） vs 上一轮快照
变了 → 红「暗改价格」+ 记录变化前后值
```

（注意区分「暗改」与「合法调价」：价卡变化本身报出来，是不是要紧由你看
快照历史判断。）

## 每条请求的展示

| 列 | 内容 |
|----|------|
| 时间 | 请求时间 |
| 模型 | 模型名 |
| 上游 | 渠道名 + 平台小胶囊 |
| 上游金额 | 实际扣的钱 |
| 我的金额 | 收的钱 |
| 利润 | 收了 − 花了（负数红色） |
| 倍率 | 真实分组倍率 vs 显示分组倍率（暗改时红字「暗改倍率」） |
| 状态 | 胶囊：正常 / 暗改倍率 / 亏本 / 无法核对 |

详情弹窗：三金额 + 列价成本 + 分组倍率对比 + 上游价卡快照变化 + tokens 明细。

兜底：收了 < 花了（亏本）直接红。

## 数据来源（全部现成）

| 数据 | 来源 |
|------|------|
| 上游显示价卡与分组倍率 | NewAPI `/api/pricing`；sub2api `/api/v1/groups/rates`（监控快照现成） |

> （缓存读 tokens 仍从输入中扣除后分别计价——这个是算对列价成本的前提，
> 保留在计算里）。

## 边界情况

| 情况 | 处理 |
|------|------|
| 上游显示价卡/分组倍率拿不到 | 灰「缺显示倍率」 |
| NewAPI 上游日志缺缓存折扣字段 | 按该上游价卡的缓存折扣计算（价卡里有） |
| 按次收费模型 | 列价成本 = 显示按次价 × 次数，其余同 |
| 输入 tokens ≤ 缓存读 | 异常数据，整条按缓存计，不出负数 |
| 判重/匹配 | 沿用现有匹配链，本设计不改动 |
