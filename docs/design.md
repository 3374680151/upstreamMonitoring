# Upstream 功能设计与业务逻辑汇总

> 来源：2026-08-26 ~ 2026-08-27 全部会话（7 个 session）的功能需求、业务规则与实现逻辑沉淀。
> 本文档按模块归纳「用户想要的功能清单」与「对应业务逻辑」，作为后续开发的统一依据。

---

## 模块一：认证与登录态

### 功能清单
1. **默认认证方式 = 浏览器自动同步**（浏览器扩展桥接登录态）。
2. **移除「手动导入登录态（token）」认证方式**（前后端全部删除）。
3. **凭据兜底保留**：站点切换到浏览器登录模式时，账号/密码/token 凭据必须保留，不允许物理删除。
4. **认证回退链**：监控/检测请求在任何认证方式下都按链条回退，而非单路径直错。
5. **同域名登录态共享**：同一注册域名的多个站点（如 `www.text168.com` 与 `api.text168.com`）自动共享登录态。
6. **浏览器扩展协作**：扩展版本演进（0.1.2 → 0.1.3 → 0.1.5），需处理 MV3 冷启动。

### 业务逻辑
- **凭据保留规则**：切换浏览器模式时，输入框留空 = 保留原凭据，填写 = 替换。原设计（切浏览器 = 只认浏览器、清空凭据）已废弃。
- **认证回退链顺序**：
  `浏览器会话不可用 → 账号密码自动登录（成功后续期会话）→ 系统 access token → 全部失败才报错`
- **同域名共享规则**：token 共享前必须先对目标站点的 `base_url` 做一次校验，校验通过才复用，避免盲共享导致失败。NewAPI 与 sub2api 均适用。
- **NewAPI refresh cookie 路径规则**：NewAPI v1.0.0+ 不在 localStorage / webpack chunks 存 token，必须读 refresh cookie，且按路径优先级探测：`/api/user/auth/refresh → /api/user/auth → 根路径`。
- **会话状态更新 SQL 必须平台无关**（不能硬编码 sub2api），否则 NewAPI 站点会卡在 `validating` 状态。
- **前端序列化必须返回真实 `auth_mode` 与 `session_sync_status`**（NewAPI 站点曾返回硬编码值）。
- **扩展冷启动**：Chrome MV3 service worker 冷启动可能超过 400ms，连接检测需实现 1600ms 重试。
- **批量同步前置检测**：开始批量同步前先探测扩展连接状态，不可用则提前中止，不进入逐站超时。

## 模块二：同步体系（多主站批量同步）

### 功能清单
1. **全局同步配置**：提供对所有主站一键同步的全局入口。
2. **同步高性能**：多级并行，整体耗时从 ~30s 优化到 ~4.8s。
3. **渠道分类内联**：渠道分类在同步过程中完成，而非同步后单独跑一轮。
4. **实时同步日志与状态**：批量同步时每个站点完成即追加状态、刷新列表。
5. **浏览器自动同步保存快速响应**：保存操作不能卡 30s。

### 业务逻辑
- **多级并行结构**（三层）：
  1. 多主站级：`ThreadPoolExecutor`，`max_workers ≤ 8`；
  2. 单主站 HTTP 级：`fetch_channels` 与 `fetch_groups` 并行；
  3. 数据处理级：`normalize_channels` 与 `normalize_groups` 并行。
- **渠道分类内联规则**：分类复用同步的同一 HTTP 响应，不发起二次请求；分类所用平台判定见模块三。
- **实时日志规则**：每站点完成立即追加完成状态并刷新列表（不等全批结束）。
- **浏览器同步保存性能参数**：探测超时 400ms、轮询间隔 200ms、最长轮询 30s；`SESSION_SYNC_TTL_SECONDS = 120`（曾因 TTL 不足报「同步请求过期」）。
- **主站同步 = 双向对账**（既有规则，继续有效）：消失的站点停用而非删除；只动 `discovery_links` 里有的；15s 自动 + 手动。

## 模块三：渠道分类与上游匹配

### 功能清单
1. **平台判定正确性**：渠道的上游平台必须按监控站点数据库记录的 `platform` 判定。
2. **避免 HTTP 探测**：平台判定不允许对上游发起额外探测请求。
3. **监控站匹配兜底**：渠道匹配监控站时字段兜底。
4. **上游分组/倍率数据采集**：低延迟、低上游压力。

### 业务逻辑
- **平台判定规则**：一律用监控站点库中记录的 platform（sub2api 站点曾被主站 newapi 平台推断覆盖，导致 6 站 404、分组拉取失败、分类数据丢失）。
- **双层缓存**：批内缓存 + 全局 `TTLCache`（1h），彻底消除 HTTP 探测。
- **监控站匹配兜底**：`upstream_base_url || channel.base_url`，与后端规则保持一致（binding 的 `upstream_base_url` 存在为空的情况）。
- **分组数据采集**：3 并发请求 + 30s TTL 缓存，避免对上游高频调用。
- **分类不猜测**：上游监控器 `group_name` 为空时后端用启发式归层，归层失败不猜测归属（宁缺勿错）。

## 模块四：主站渠道页 UI

### 功能清单
1. **「当前 key 上游倍率」列**：去掉多余信息，聚焦当前 key 的倍率展示。
2. **hover 浮层查看全貌**：鼠标悬停倍率时弹出浮层，展示上游分组倍率全量目录。
3. **双平台浮层对齐**：sub2api 站点的倍率弹窗与 NewAPI 行为一致，可点击查看。
4. **弹窗自动关闭**：站点添加/编辑保存完成后页面自动关闭（不留残留弹窗）。

### 业务逻辑
- **浮层展示规则**：单一目录视图，展示全量分组倍率；当前 key 命中的分组排在最前并高亮标注。
- **上游不允许监控展示规则**：sub2api 分组无模型健康数据（监控器无法归属分组 / 上游未配置监控器，如 bugteam / 悠米 / mengyu）时，浮层与倍率弹窗的「模型状态」列直接显示「上游不允许监控」（warning 色文案），不再渲染空的「暂无成功率 / 模型 0/0」汇总。判定条件：模型健康缓存已加载、无读取错误、该分组模型列表为空。
- **sub2api 浮层数据源**：使用 `api.siteModels()`（模型健康缓存数据）；原逻辑对 sub2api 直接 return 不发请求，已修复为双平台同逻辑。
- **性能指标数据源差异**：`pricing / perf-metrics` 接口仅支持 NewAPI；sub2api 协议本身无成功率/延迟/TPS 指标，浮层对 sub2api 不展示模型状态与成功率属预期行为。
- **弹窗关闭规则**：新增/编辑成功即自动关闭（显式关闭规范的延续）。

## 模块六：数据与分支治理

### 业务逻辑 / 约定
- **数据库清理**：清数据但保留表结构、迁移记录与空配置行，自增 ID 重置；清库后必须重启后端（清进程内模型缓存、SchedulerWorker、锁字典）。
- **分支纪律**：
  - 一条分支同一时刻只能在一个目录检出；多会话并行开发用 git worktree 独立目录，避免互相干扰。
  - 修复验证通过后才合 master；已合入的旧分支及时删除。
- **主站是 aiinfinite.online**（id=2，manman）：任何测试/脚本严禁用 `main.example` 假数据覆盖真实主站。
- **后端缺失 import 是 500 高发原因**（`_site_session_sync_request_error` / `request_json` / `is_admin_site_row` 等），改动后需扫描未定义名。
