# 余额批量查询稳定性设计

## 背景与根因

余额页的单站点查询和“一键查询”最终调用同一个 `/api/sites/:id/account` 接口。
单站点操作每次只产生一个上游请求；当前“一键查询”在
`apps/web/src/lib/useBalances.ts` 中使用 `Promise.all`，会在同一时刻向全部上游站点
发起请求。后端是多线程 HTTP 服务，因此这些请求会同时建立外部连接。

用户反馈单独查询稳定，而批量查询偶发出现 HTTP 400、连接被上游重置等错误。后端的
余额请求没有共享 Cookie、连接或认证状态；差异集中在批量并发扇出，符合上游或网络链路
对瞬时并发敏感的表现。

## 目标

- 让“一键查询”复用单站点查询的稳定请求节奏。
- 一个站点失败时继续查询后续站点，并保留每行独立的成功/失败状态。
- 保留现有汇总提示、按钮忙碌态和 API 响应契约。
- 不改变余额数据结构、认证方式、后端接口、数据库或页面视觉样式。

## 设计

将 `queryAll` 从 `Promise.all(sites.map(...))` 改为按 `sites` 顺序逐个 `await
queryOne(site, false)`。每次请求完成后才开始下一个请求；`queryOne` 已经负责写入对应行
的 loading、success 或 error 状态，因此无需新增共享队列或后端限流逻辑。

批量流程继续收集每个查询的布尔结果，沿用当前成功数/失败数汇总文案。单站点按钮在批量
忙碌期间继续禁用，避免用户额外制造并发；批量按钮的 loading 状态保持不变。

不采用限制为 2 的并发：它仍可能复现上游瞬时并发问题，且没有证据表明 2 是安全阈值。
不增加自动重试：余额查询可能触发 sub2api 密码登录或令牌刷新，重复请求会放大限流与
登录态轮换风险，且会掩盖真实错误。

## 测试

- 添加前端源码回归测试，确认批量流程按顺序 `await queryOne`，不再调用 `Promise.all`
  扇出。
- 运行现有 Web Node 测试和生产构建，确保类型、页面行为及其他调用不受影响。
- 运行 Python 编译检查；本次不修改后端逻辑，因此不新增数据库集成依赖。

## 范围

本修复只涉及余额页的批量调度逻辑。不会清理或迁移 `data/app.db`，不会修改 MySQL
数据，也不会改变 NewAPI / sub2api 的账户接口调用。
