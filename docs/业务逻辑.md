# 页面一 登录（LoginPage）

**「登录」按钮**（`components/LoginPage.vue` → `POST /api/auth/login`，`core/security.py`）

**规则**：密码只在服务端 `.env` 的 `CONSOLE_PASSWORD`；登录换发 token 存浏览器，之后每请求带 Bearer。比对用 `compare_digest`（防时序侧信道，非 ASCII 密码 TypeError 坑已处理）。任何接口 401 → 前端清 token、广播 `console-unauthorized`、退回登录视图。密码留空 = 鉴权层整体关闭（仅限本机/内网）。公开路径白名单只有 auth 三件套 + session-sync complete（扩展靠一次性 secret，见页面四）。

**分叉**：

| 情况 | 系统怎么走 | 界面显示 |
|---|---|---|
| 密码正确 | 签发 token → 存 localStorage → 进入控制台 | 「登录成功」toast，正常渲染页面 |
| 密码错误 | 401 信封 `{code:"unauthorized"}` | 登录页内红条显示后端 message |
| 未设密码（留空） | 所有 `/api/*` 免鉴权，`authRequired=false` | 直接进控制台，无登录页 |
| 已登录但 token 过期 | 任意请求 401 → 清 token → 退登录页 | 回到登录视图（数据已加载的页面被替换） |

# 页面二 总览（OverviewPage）

**页面数据**（`useConsoleData`，15 秒轮询）

**规则**：五张 KPI 是纯前端聚合；数据来源就是轮询的渠道列表，没有独立总览接口。

**分叉（渠道状态如何计入 KPI）**：

| 渠道状态 | 计入哪张卡 |
|---|---|
| enabled 且 status=ok | 「启用中」+「正常」 |
| enabled 且 warning / failed | 「启用中」+「异常」（异常卡红色高亮） |
| enabled 且 unknown（从未检测） | 「启用中」 |
| enabled=0（停用） | 只进「监控渠道」总数，不进启用/正常/异常 |

**「主站健康」面板**（`MainSiteHealthPanel.vue` → `GET /api/admin/sites` + 逐主站读渠道）

**规则**：只在进入页面和手动「刷新」时拉取，不跟轮询（对每个主站都真实打管理接口，跟轮询等于持续骚扰上游）。

**分叉（主站渠道状态归类）**：

| 上游返回 | 归类 | 是否需要人管 |
|---|---|---|
| NewAPI status=1 | 运行中 | 否 |
| NewAPI status=2（手动停用） | 已停用 | 否——自己关的 |
| NewAPI status=3（自动停用） | **异常** + 进红条 | **是**——上游判渠道连续失败自动关的 |
| sub2api active | 运行中 | 否 |
| sub2api disabled | 已停用 | 否——**正常停用状态，不当故障报** |
| 主站整体读失败 | 保留上次成功数据 + 黄条列出原因 | 看原因（多为登录态/网络） |

**分叉（「重新启用」链接点击后）**：`PUT .../channels/{cid} {status:1}` → 后端走**专用接口** `POST /api/channel/:id/status`（`set_newapi_channel_status`）。为什么绕开通用 PUT：NewAPI 的 PUT 只要 body 带 `status` 就无条件返回 Invalid parameters（当时逐字段二分验证的结论）；且该接口只接受 1/2——**3 不允许外部设置**（自动停用是上游自己置的位，只能由上游恢复或人工改配置后走 1）。

| 结果 | 界面显示 |
|---|---|
| 成功 | 「已重新启用渠道」toast + 面板自动重读 |
| 失败 | 红条内追加错误原因 |

# 页面三 主站监控（ChannelsPage）

## 3.1 主站下拉切换

**分叉**：

| 情况 | 系统怎么走 | 界面显示 |
|---|---|---|
| 正常切换 | 三路并行拉渠道/分组/绑定汇总 | 渠道表刷新 |
| NewAPI 主站、本会话首次进入 | 额外自动跑一轮全渠道倍率匹配（每会话每主站只一次，`claimAutomaticRefresh`） | 各行出现「匹配中...」转圈后出倍率徽章 |
| 凭证缺失的主站 | 读取失败 | 选项文案带「未配置令牌/密码」标注，表格区报错横幅 |

## 3.2 「同步主站」（对账导入，`sync_service.auto_sync_admin_site_channels_to_sites`）

**规则（执行顺序，刻意的）**：先读全量 → **先落快照**（`admin_site_sync_state`，带 hash）→ 候选聚合（按注册域名，`api.example.com` 与 `vip.example.com` 同家合并；IP/localhost 不合并）→ 按范围过滤 → 逐候选建站/复用 → 写来源关联 → 关联对账 → 渠道对账。**任何一个 NewAPI 渠道 base_url 非法 → 整次同步拒绝执行**（宁可不同步，不在上游数据不完整时做删除类清理）。多主站并发（池上限 8）。**同步本身不刷 key**——响应里 `keys_*` 计数恒为 0（兼容保留字段），key 刷新职责在 3.9/3.10。同步失败不覆盖上次成功快照（只记错误）。

**分叉一（范围怎么选，弹窗 `SyncScopeDialog`）**：

| 情况 | 系统怎么走 |
|---|---|
| sub2api 主站 | 不弹范围框，直接按 all 执行（渠道无上游 base_url 可发现） |
| NewAPI 主站 | 弹框，预选 = 主站行 `sync_all_channels`（true→全部 / false→仅识别） |
| 选「勾选渠道」但没勾 | 「开始同步」按钮禁用 |
| 渠道监控页的「同步主站」 | 不弹框，全部主站一把梭（scope 按各主站自己的行配置） |

**分叉二（范围=仅识别 时平台不符的站点）**：**平台识别只在「仅识别 / 勾选」范围下运行**（「全部渠道」不做识别、自然也不产生平台删除）。识别不中的候选不导入，**且本地已关联但平台不符的站点直接删除**（`_delete_platform_mismatch_site_links_in_connection`）——全系统唯一主动删站点的路径，所以它是显式选项。全部/勾选 范围下平台不符的站点**不动**。

**分叉三（对账时渠道 vs 本地站点，`_apply_admin_site_channel_reconcile_in_connection`）**——判定依据是**来源关联**，不是渠道名：

| 情况 | 系统怎么走 | 界面/结果 |
|---|---|---|
| 站点名下还有活 link | 站点不动 | — |
| 上游渠道消失（link 全失效）+ 模式 disable | 站点停用 + 打 `auto_disabled` 标记 | 计入「停用 N」；历史全保留 |
| 上游渠道消失 + 模式 delete | 站点连同快照/变化删除 | 计入「删除 N」；**不可恢复** |
| auto_disabled 的站点重新拿到活 link | 自动恢复启用 | 计入「恢复 N」 |
| 同一渠道历史上挂在多个站点 | 本轮保留规范站点（优先本轮归属，否则最老 link），其余 link 释放 | 用户无感 |

**分叉四（单个候选的导入结果，`_import_discovered_site_item`）**：

| 结果 | 条件 |
|---|---|
| created | 该 URL（或同注册域名）本地无站点 → 新建（token 模式、login_enabled=0、状态 unknown） |
| existing | 已有站点 → 复用 + 补写/更新来源关联 |
| conflict | 同 URL 已存在**非 NewAPI** 平台站点且不允许复用 |
| invalid | URL 非法 / 渠道 ID 非法（主站同步路径 URL 非法直接整体拒绝，见上） |

## 3.3 「刷新倍率」工具栏按钮（全量批次）

**规则**：`ratio` 模式**复用已保存的 key** 重新匹配全部渠道——不碰主站 key 接口，所以平时**不需要 2FA**（proof 缺失时前端才拦，见 3.5）。批次开始先清上游分组 30s TTL 缓存（保证本轮最新倍率，之后同上游多渠道共享一次分组请求）。批次放内存不放表——重启即清，下次触发重建。

**分叉**：

| 情况 | 系统怎么走 | 界面显示 |
|---|---|---|
| 批次已在跑 | 幂等返回当前进度（`already_running`） | 徽章继续「N/M」 |
| 同 mode 同渠道集的 paused 批次 | **断点续跑**（done/failed 保留） | 从断点继续出进度 |
| 单渠道 key 读到 2FA/proof 类失败 | 整批 `paused`，取消在途 worker | 徽章红「倍率刷新已暂停，需重新验证 2FA」 |
| 单渠道普通失败 | failed+1，批次继续 | 完成徽章「成功 N/M，失败 X」 |
| 全部跑完 | status=done + 自动重载列表 | toast「倍率全量刷新完成：成功 N/M，失败 X」 |

## 3.4 NewAPI 渠道表徽章列（展示优先级 = 修复顺序）

**分叉（一行显示哪个徽章，`newApiRows`）**：

| 优先级 | 情况 | 徽章 | 颜色 |
|---|---|---|---|
| 1 | 同源监控站点登录态失效（auth_ready=false 或匹配被 401 拒） | **站点未登录**（有旧倍率则显示虚线旧值） | 警示 |
| 2 | 匹配到但部分分组上游已不存在 | 上游分组不存在 | 警示 |
| 3 | key 在上游列表找不到 / 没绑分组 | 上游 key 未匹配 | 警示 |
| 4 | proof 失效 | 需要安全验证 | 警示 |
| 5 | 没读到真实 key | 缺少渠道 key | 警示 |
| 6 | 其余未命中 | 上游未匹配 | 中性 |
| — | 全部匹配成功 | 实线倍率徽章（可悬浮看全组目录） | 绿/警示 |

**设计意图**：站点没登录一律归「站点未登录」——先修登录态再看 key 的问题，键序就是修复顺序。**虚线徽章 = 上次成功数据**（登录态挂了但匹配过倍率：显示旧值 + 悬浮注明，数据降级但不消失）。浮层读缓存（秒开）、倍率弹窗走实时（refresh=1）——分工：浮层要快、弹窗要准。

## 3.5 单渠道「刷新倍率」按钮（`channel_match_service.match_channel_upstream`）

**总原则：宁可不给数，不给错数；临时故障不毁旧数据。**

**规则（顺序刻意的四步）**：① 先看上游登录没登录再看 key——不就绪**止步**，故意不取 key（取 key 可能要 2FA，上游没登录取了也白取，还耗主站验证状态、有触发限流风险）；② key 三级来源（`admin_channel_keys` 缓存 → 详情明文（**掩码形态直接弃用**）→ proof 受保护接口），90% 刷新不碰主站；③ 读 key 有节流闸门（按主站串行 + 最小间隔，429 触发全站冷却 30 秒）；④ 精确匹配不猜——早期「拿分组名猜匹配」的路径已删掉，成本算错比不显示更糟。

**分叉（完整决策树）**：

| 步骤 | 情况 | 系统怎么走 | 界面显示 |
|---|---|---|---|
| ① | 找不到同 base_url 监控站点 | 直接返回 | 「上游未匹配」+ 悬浮「请先在站点监控添加该上游」 |
| ① | 监控站点登录态未就绪 | **止步**（不取 key） | 「站点未登录」 |
| ① | proof 缺失（前端先拦） | 弹 2FA 弹窗，验证通过自动续跑本动作 | 「重新验证主站 2FA」弹窗 |
| ②③ | key 缓存命中 | 直接用，不打主站 | — |
| ②③ | 详情 key 是掩码 | 弃用，走受保护接口 | — |
| ②③ | 受保护接口要 proof / 429 | proof 失效→`needs_key_verification`；429→冷却内直接拒绝并告知等待秒数 | 「需要安全验证」/ 行下红字「已暂停请求，请等待约 N 秒」 |
| ④ NewAPI | key 在登录账号 /api/token/ 列表找到（掩码命中→按 id 取全量复核） | 拿到分组名 | — |
| ④ NewAPI | 找不到（上游明确说没有） | `key_not_found`，**清旧倍率** | 「上游 key 未匹配」 |
| ④ NewAPI | 找到但没绑分组 | `no_group`，**清旧倍率** | 「上游 key 未匹配」· 悬浮说明 |
| ④ NewAPI | 网络超时 / WAF / 限流 / 2FA 过期 | `error`/`refresh_error`，**保留上次成功倍率、不动 matched_at** | 虚线旧倍率 + 悬浮原因 |
| ④ NewAPI | 读到分组，倍率目录也通 | 组齐 → `matched`；有组已不在目录 → `matched_partial`（旧倍率回填未拿到的组，避免整行变 —） | 实线倍率徽章 /「上游分组不存在」+ 兜底值 |
| ④ sub2api | key 在 /api/v1/keys 列表找到 | 拿到分组；二开路由型 key 再走用量定位（下一行） | — |
| ④ sub2api | key 不在列表 → **先试探网关**（真 key 打 /v1/models 200 **且废 key 对照被 401/403 拒**才算数） | 网关认 →「key 有效但属于其他账号」；网关不认（或对照也 200=这站不验鉴权，试探不可信）→ `key_not_found`（真的没了） | 红字提示换绑/重同步 vs 「上游 key 未匹配」 |
| ④ sub2api | 分组不在可见目录 | `matched_partial` + key 记录基础倍率兜底（message 明确「基础值非实时」） | 「上游分组不存在」+ 倍率徽章 |
| ④ sub2api | 路由型 key（多 routing_groups） | **最近一次用量日志**定位实际计费分组（组 id + rate_multiplier）；没用量 → priority=1 主分组 | message 注明「按最近用量定位，实际计费倍率」/「暂无用量，按主分组展示」 |
| ④ sub2api | 密码模式上游 | 一次登录两用（读分组的 token 复用读 key 列表）；登录会话**用完即弃**，不写回站点行 | — |
| ④ 其他平台 | 不支持 | `unsupported` | 红字「暂不支持上游平台」 |

## 3.6 单渠道「刷新 key」按钮（`POST .../channels/{cid}/key/refresh`）

**规则**：全局一次只允许一个（前端互斥）——每次读 key 都可能触发 proof 校验与限流闸门，并发跑会打挂主站接口、冷却连累全部渠道。强制重读（绕过缓存）→ 比对 → 变了立刻重新匹配倍率（一次按钮两件事）。

**分叉**：

| 情况 | 结果 | 界面显示 |
|---|---|---|
| 首次读到 | `first_fetch` | 「真实 key 已保存，倍率已刷新」 |
| key 与缓存不同 | `changed` | 「key 已更新，倍率已刷新」 |
| key 相同 | — | 「key 已是最新，倍率已刷新」 |
| 读 key 遇 429 | 429 + `rate_limited` | 红字 + 等待提示 |
| 读 key 遇 proof 失效 | `security_verification_required` | 自动弹 2FA 弹窗 |
| 其他失败 | `key_refresh_failed` | 红字原因 |
| key 读到但倍率匹配失败 | — | 「key 已保存，但倍率刷新失败：原因」 |

## 3.7 「重新验证主站 2FA」弹窗（`verify_admin_site_channel_key_access`）

**规则**：读 key 接口要求**网页登录态**（系统令牌被 NewAPI 故意拒绝，安全验证只认 session-bound token）；网页登录开 2FA 且 session 会过期 → 验证一次换短期 `proof_token` 存主站行，有效期内免验证。**验证必须用本次动态码强制重新登录**（force=True 忽略旧会话）——旧会话可能没经过 2FA，拿它跑 /api/verify 会报"2FA 未认证"：**动态码必须花在经过 2FA 的会话上**。

**分叉**：

| 情况 | 系统怎么走 | 界面显示 |
|---|---|---|
| 验证成功 | 存 proof + 立即启动全量 key 批次 + 给 key_sync 设 60 秒保护期（防自动更新抢跑撞限流）+ 自动续跑你刚才点的动作（含恢复 paused 批次） | 「主站 2FA 验证通过」→ 自动继续 |
| 验证码错误 | proof 不签发 | 弹窗内红条，可改码重试 |
| 网页登录失败（密码错等） | 不签发 proof | 弹窗内红条原因 |
| proof 之后失效 | 上游返回 SECURITY_PROOF_REQUIRED/INVALID/EXPIRED → 后端自动清空 proof | 下次操作重新弹验证 |
| 网页 session 过期（读 key 中途） | 后端先用 refresh cookie 强刷 session 重试一次，救不回才要求重新验证 | 用户无感 / 最终提示验证 |

## 3.8 「编辑优先级」/ sub2api 编辑与启停

**规则（NewAPI 更新的坑，当时逐字段二分验证）**：NewAPI 的 PUT 是**整体替换**且 body 带 `status` 必失败 → 更新实现是「读回整个渠道对象 → 合并要改的字段 → 剔除 status/空 key/派生只读字段 → 整体回传」；合并基底必须是上游原对象——白名单漏掉任何可写字段都会被清空。改 key 时同步更新本地 key 缓存。状态修改走专用 `POST /api/channel/:id/status`（只接受 1/2）。sub2api 写入只认白名单字段（白名单外 400）；保存的是差异（无修改不发请求）；账户统计规则的账户 ID 只编辑配置里已有的（不碰号池）。

**分叉**：

| 情况 | 系统怎么走 | 界面显示 |
|---|---|---|
| NewAPI 优先级保存成功 | 读回-合并-剔除-status 走专用接口（若传了）-PUT | 「优先级已更新」 |
| sub2api 保存成功 | 校验白名单 → 只传差异 → PUT 写回主站 | 「配置已保存」 |
| patch 无变化 | 不发请求 | 「没有需要保存的修改」 |
| sub2api patch 含白名单外字段 | 后端 400 | 红条校验错误 |
| 启停（sub2api） | active↔disabled，普通状态切换 | 「已启用/已停用」（disabled **不算故障**，对比 NewAPI status=3） |

## 3.9 自动更新渠道 key（主站开关，`run_due_admin_key_syncs`）

**规则**：一次只更新 `fetched_at` **最旧的一个**渠道（负载恒定，20 个和 2000 个渠道成本一样）；优先刷 proof 签发时间之后没刷过的渠道（和 2FA 批次互补不重复劳动）；key 变了立刻重新匹配倍率（匹配失败静默——下轮自然重试）。

**分叉（失败退避，按类别不同策略）**：

| 失败类别 | 退避 | 界面显示（主站弹窗状态块） |
|---|---|---|
| 429 / 限流 | 1/2/5/15/30 分钟阶梯（按连续失败次数） | 「更新失败」+ 暂停至时间 |
| 2FA / proof / 安全验证 | **固定 30 分钟**（自动重试也过不了，等你去验证） | 同上 + 失败原因 |
| 其他（网络等） | max(间隔,5) 封顶 30 分钟 | 同上 |
| 成功 | 清零失败计数，下次 = interval 分钟后 | 「更新成功」+ 最近/下次尝试时间 |
| 批次余量未清 | 下一轮 tick 立刻续跑不傻等 | — |

## 3.10 「添加主站 / 编辑主站」弹窗

**规则**：NewAPI 两套凭证各干各的（系统令牌+用户 ID 读渠道/分组/更新；网页账号密码只为 key 读取与 2FA）；sub2api 只认管理员邮箱+密码（不支持 API Key/手动 token/2FA/Turnstile——开了就连不上，是边界不是缺陷）；「测试连接」不必先保存，且**表单值优先、已存值补位**（改一半也能测没改的部分）；Base URL 拒绝带 userinfo 的 URL；三个同步配置（范围/消失处理/快照保留）全部按主站行下沉——危险选项按主站授权而非全局误伤。

**分叉（测试连接）**：

| 情况 | 系统怎么走 | 界面显示 |
|---|---|---|
| NewAPI 凭证齐 | 令牌读分组接口 | 「连接成功：可见 N 个分组」 |
| NewAPI 凭证缺 | 本地校验拒绝，**不发请求** | 「请填写系统访问令牌和用户 ID」 |
| sub2api | 真实登录拿 token → 读渠道数（测完整登录链路） | 「连接成功：可见 N 个渠道」 |
| sub2api 登录失败 | 按失败分类给原因 | 红条 + 上游原始错误 |
| 平台与已存配置不一致 | 拒绝 | 「主站平台与已保存配置不一致」 |

## 4.1 工具栏「同步 sub2api / NewAPI 登录态」

| 情况 | 系统怎么走 | 界面显示 |
|---|---|---|

## 4.2 行内「同步」（登录态引导弹窗，`useLoginAssistSync` + `session_sync_service`）

**规则（后端协议）**：前端建请求（一次性 secret **只存哈希**、TTL **120 秒**；同站点旧 pending 请求立即标 `expired/REPLACED`——同时只允许一个在途）→ 扩展抓登录态（字段白名单外拒收）直接 complete → 后端**先验证再落库**（拿会话真实请求一次上游，防半失效 cookie 造成假"已同步"）→ **终态原子化**（先落库再返回，六种终态）→ 竞态防护（扩展验证耗时数秒，期间你重开同步/改认证方式——凭证写回前重读请求与站点行，**旧请求的完成结果不允许覆盖新状态**）。

**分叉（弹窗状态机 + 终态）**：

| 探测结果 | 系统怎么走 | 界面显示 |
|---|---|---|
| ready | 关弹窗；NewAPI 开兜底开关则顺手 force 刷新兜底令牌 | 绿「登录态已同步」toast |
| no_session（第一次） | 自动打开站点登录页 | 黄「等待登录完成」+ 提示 |
| no_session（之后） | 不再自动开页 | 黄「仍未检测到，请确认登录成功再点我已登录完成」 |
| permission_required | 止步 + 给**具体修复指引** | 红 +「chrome://extensions → 网站访问权限设为所有网站」 |
| extension_unavailable | 止步 + localhost 要求说明 | 红「扩展未连接」 |
| expired / failed | 止步 + 原因 | 红，可点「重试」 |
| 用户点「我已登录完成」 | 手动触发下一次探测（**不自动轮询**——自动轮询会在你没登录完时反复探测） | 转圈 → 跳上表对应分支 |

**后台自愈**（`useAutoSessionResync`）：扩展在线时自动给已失效渠道重发同步——你在上游页面重新登录了，不用回来挨个点。

## 4.3 行内「检测」按钮（`detect_site` 完整回合）

**规则（顺序）**：① 采集（NewAPI：公开 `/api/user/groups`；开认证增强再单独第二轮 `/api/user/self/groups`——该账号真实倍率含隐藏组。sub2api：`/api/v1/groups/available`，认证优先级固定 浏览态→refresh_token→密码）；② 成功 → 模型名单从**缓存**并入（检测热路径不发模型请求——sub2api 密码模式每次请求都是真实登录，频繁登录必触发风控）→ 写 success 快照；③ 与**最近一次成功快照** diff（`get_last_success_snapshot` 按 status='success' 取——**中间的失败快照不参与比较**，网络抖动恢复后不会冒假变化）；④ 变化落库 + 推送；⑤ 更新站点行与 next_check_at。

**分叉一（采集失败的归因，`site_failure_kind`——顺序就是判定顺序）**：

| 归因 | 判定依据 | 界面徽章 | 处理指引 |
|---|---|---|---|
| waf | 响应是 HTML 挑战页（cf-mitigated 头 / Cloudflare 特征 / WAF 状态码 403/503 等） | 黄「防护拦截」 | **与登录态无关**——换出口（VPN/代理）下一轮自动恢复 |
| auth_expired | 浏览器态缺失 / sub2api 认证错误 / HTTP 401、403 | 红「登录态已失效」 | 去行内「同步」重新登录同步 |
| network | 错误文本含 timeout/connection reset/DNS/SSL 等 | 黄「网络异常」 | **与登录态无关**——查本机网络 |
| 其他 | 都不匹配 | 只记 last_error，不给归因徽章 | 看详情页原始错误 |

**设计意图**：WAF 和网络**故意不**标成登录失效——这两类跟登录无关，引导用户重新登录是误导。

**分叉二（失败后的状态升级）**：

| 连续失败次数 | status | 说明 |
|---|---|---|
| 1–2 次 | warning | 单次抖动不配红色 |
| ≥3 次 | failed | 连续证据够了才升级 |
| 任意一次成功 | ok + 计数清零 | — |
| 公开采集成功但认证增强失败 | warning + login_last_error | **公开数据照常更新**——登录增强挂了不连坐基础监控 |

**分叉三（diff 产出）**：

| 情况 | 系统怎么走 |
|---|---|
| 两侧快照都有模型名单 | 逐组比较 → 可能产生 模型上架/下架 变化 |
| 任一侧缺模型名单 | **跳过该组模型 diff**——「没数据」绝不当「全部下架」报 |
| 同组多字段变了 | 产生多条不同类型的变化（倍率变了+描述也变了 → 两条记录） |
| 有变化 | 逐条 INSERT changes（severity：整组消失=critical、模型下架/涨价=warning）→ 推送 |
| 无变化 | 不写不推，只更新状态与快照 |

**分叉四（前端自动重试）**：检测失败且原因是浏览器登录态缺失（sub2api 浏览器模式）→ 自动尝试扩展同步后**重试一次**——很多"失败"其实是会话刚过期。

**行内「倍率」按钮（弹窗）**：打开即实时穿透（refresh=1 强刷并回填缓存）——与主站页悬浮浮层的缓存路径分工：浮层要快、弹窗要准。models/pricing 路由是 SWR：有过期缓存先返回（标 refreshing）+ 后台刷新——永远立即有数据看。sub2api 分组无模型数据 → 如实显示「上游不允许监控」（不装正常）。NewAPI 模型状态来自 `/api/perf-metrics/summary`（模型级汇总不是分组级）——弹窗里明确标注，避免误读。

**行内「⋯ 更多 → 删除」**：二次确认 → `DELETE /api/sites/{id}`。**快照、变化记录、来源关联、同步请求全部外键级联删除**（schema ON DELETE CASCADE），模型缓存顺手失效。为什么用数据库级联：低频操作，级联保证不留孤儿，应用层漏删一张表就是事故。

# 附 A：全局底座规则

**调度器**（`workers/scheduler.py`）：每 `SCAN_INTERVAL_SECONDS` 扫 `next_check_at` 到期渠道逐个检测——**渠道间节奏互相独立**，一个卡死不拖累别人；停机走 `STOP_EVENT.set()`（在跑的一轮在站点间隙自然退出，不硬杀）；`max_instances=1 + coalesce=True`（不叠加扫描、错过的触发只补跑一次）。另两个 job：每 24h 快照保留清理；启动时 `ModelCacheWorker.warm()` 预热（不阻塞 HTTP 启动）。

**15 秒前端轮询**：渠道列表、变化、推送设置；「主站健康」「主站渠道表」例外（各自进入/手动时拉）——**哪些数据能自动刷、哪些省着打上游，按接口成本划线**。

**出站 HTTP**（`integrations/http.py`）：httpx 共享 Client（`trust_env=False`——不读系统代理，代理变量会把上游流量引偏）；被上游重置时回退 curl_cffi（TLS 指纹伪装），仅此一层。

**快照保留**（每 24h）：按主站 `retention_days` 圈定**该主站导入的站点**（经 site_discovery_links），删过期快照与变化；0=永久。手动添加的站点永不被清理——保留天数是你对"主站衍生数据"的态度，不外溢到手工资产。

**平台识别**（`platform_detect_service.py`）：先试 NewAPI 公开接口（通=newapi）→ 再探 `/api/v1/auth/me`：200 或 **401/403** 都算 sub2api（401=端点存在只是要鉴权，404 才是不存在）→ unknown。三层缓存（同批 → DB 已有 platform → HTTP 探测），探测命中回写 sites.platform 下次零探测。

# 附 B：两条链路的完整走位（含全部分叉标注）

**渠道行「检测」**：
```
POST /api/sites/{id}/check → detect_site
  ① 采集 ──失败──▶ failed 快照 + 归因(waf/network/auth_expired) + 状态升级(≥3 异常) ──▶ 结束
         └──成功──▶ ② 模型名单并入(只读缓存) → ③ success 快照
  ④ diff（基准=最近成功快照；认证增强单独第二轮；两侧有名单才比模型）
  ⑤ 变化 ──有──▶ INSERT changes（severity 分级）→ notify（通道开关守卫→分块正文→写日志）
         └──无──▶ 只更新状态
  ⑥ 更新站点行（状态/清零/next_check_at/当前分组缓存）
```

**主站渠道行「刷新倍率」**：
```
（proof 缺失？→ 弹 2FA → 强制重登+/api/verify → proof + 自动启批次 + 续跑原动作）
→ POST .../match → match_channel_upstream
  ① 同源监控站点登录态就绪？ ──否──▶ 止步「站点未登录」（故意不取 key）
  ② key 三级来源：admin_channel_keys 缓存 → 详情明文(掩码弃用) → 受保护接口(节流闸门：按站串行+最小间隔+429 冷却 30s)
  ③ newapi：/api/token/ 精确匹配 ──明确找不到──▶ key_not_found（清旧倍率）
                                      └─网络/WAF/限流/2FA──▶ error（保旧倍率+matched_at 不动）
     sub2api：/api/v1/keys 精确匹配 ──不在列表──▶ 网关试探（真 key 200 且废 key 对照 401/403 才算数）
                                      ├─网关认──▶ 「key 有效，属于其他账号」
                                      └─不认──▶ key_not_found
  ④ 分组倍率：命中组 available_to_login ──组没了──▶ matched_partial + key 基础倍率兜底
     路由型 key ──▶ 最近用量日志定位实际计费分组；无用量 ──▶ priority=1 主分组
  ⑤ persist：临时失败保旧倍率+matched_at；结论性失败（key_not_found / no_group）才清
→ 前端：实线=实时 / 虚线=上次成功 / 状态徽章=具体原因（键序=修复顺序）
```
