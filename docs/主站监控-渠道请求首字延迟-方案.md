# 主站监控「渠道请求首字延迟」方案

> 状态：设计稿（2026-09-07）。接口契约以 **Apifox（project 8772928）为唯一权威**，本文是实现设计记录；两者若有出入以 Apifox 为准。
> 交付形态：主站监控页（`/channels`，`ChannelsPage.vue`）NewAPI 渠道表新增「最近请求首字」列。

---

## 1. 背景与目标

在主站监控页查看每个主站渠道最近的请求质量：每渠道展示最近若干次请求的**首字延迟（TTFT，Time To First Token）**，用 10 个色点呈现趋势，按阈值着绿 / 橙 / 红。阈值不写死在代码里，全部走环境变量，方便后续调整。

数据来源：主站 NewAPI 的管理日志接口（`/api/log/`）。后端目前没有任何日志集成，属纯新增；sub2api 上游无等价日志接口，不支持。

## 2. 展示规则

每渠道固定 **10 个槽位色点**（左 = 最新）：

1. **取数窗口 = 最近 1 小时**（可配）：窗口内取最近 ≤10 次请求，按首字延迟着色——**<8s 绿 / 8–15s 橙 / ≥15s 红**；窗口内不足 10 次时，缺位补灰点。
2. **超过 15 分钟的请求**（可配）视为旧请求：色点改为**空心圆环**（同色描边），悬浮说明「约 N 分钟前的请求（非实时）」。
3. **窗口内一直没有任何请求**的渠道：整组 10 个灰点，悬浮说明「最近 1 小时内无请求」。
4. 每个点悬浮显示：首字延迟、模型名、请求时间、旧请求说明。
5. **非流式请求**没有「首字」记录，回退用总耗时（`use_time`），并保留 `is_stream: false` 标识口径。
6. 列头 `title` 说明阈值口径（如「最近 10 次请求首字延迟（<8s 绿 / 8–15s 橙 / ≥15s 红，阈值可配）」）。
7. 刷新时机：进入页面 / 切换主站随 `load()` 拉一次 + 工具栏「刷新请求」按钮（强制刷新）；**不做自动轮询**（避免频繁打主站管理接口，与主站健康面板同一约束）。
8. sub2api 主站：接口返回 405，前端不渲染该列。

## 3. 环境变量（全部可配）

| 变量 | 默认 | 取值范围 | 说明 |
|---|---|---|---|
| `MAIN_CHANNEL_TTFT_FAST_SECONDS` | 8 | 1–600 | 绿色阈值（秒）：首字延迟低于该值为 `fast` |
| `MAIN_CHANNEL_TTFT_SLOW_SECONDS` | 15 | 1–600 | 红色阈值（秒）：达到该值为 `slow`，两者之间为 `normal`（橙） |
| `MAIN_CHANNEL_RECENT_REQUESTS` | 10 | 1–50 | 每渠道展示的请求条数上限 |
| `MAIN_CHANNEL_RECENT_WINDOW_SECONDS` | 3600 | 60–86400 | 取数窗口（秒），默认 1 小时 |
| `MAIN_CHANNEL_REQUEST_STALE_SECONDS` | 900 | 60–86400 | 旧请求阈值（秒），默认 15 分钟；超过则 `stale=true` |

- 在 `backend/core/config.py` 用 `_env_int` 模式读取，进程启动时生效；修改 `.env` 后需重启实例。
- 同步补 `.env.example`（带中文注释）与 README 配置表。

## 4. 接口契约

### 4.1 请求

```
GET /api/admin/sites/{admin_site_id}/channels/recent-requests?channel_ids=1,2,3&refresh=0
```

| 参数 | 位置 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|---|
| `admin_site_id` | path | integer | 是 | — | 主站 ID（`admin_sites.id`） |
| `channel_ids` | query | string | 是 | — | 逗号分隔的主站渠道 ID，如 `1,2,3`；上限 100 个 |
| `refresh` | query | integer | 否 | 0 | `1` = 绕过新鲜缓存强制重新拉取；`0`/缺省 = 使用 60 秒内缓存 |

鉴权：沿用 admin_sites 域现有 `require_console_auth`，无新增公开路径。

```json
{
  "success": true,
  "data": {
    "admin_site_id": 3,
    "platform": "newapi",
    "thresholds": {

      "stale_seconds": 900,

    },
    "channels": {
      "12": {
        "channel_id": 12,

        "requests": [
          {

}
```

### 4.3 响应字段逐项说明

`data`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `admin_site_id` | integer | 主站 ID |
| `platform` | string | 主站平台，本接口仅 `newapi` |
| `thresholds` | object | 后端生效的阈值，前端用于悬浮说明与图例，见下 |
| `channels` | object | key 为渠道 ID 字符串，value 见下 |
| `fetched_at` | string(date-time) | 本次响应生成时间 |

`data.thresholds`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `fast_seconds` | number | 绿色阈值（秒），来自 `MAIN_CHANNEL_TTFT_FAST_SECONDS` |
| `slow_seconds` | number | 红色阈值（秒），来自 `MAIN_CHANNEL_TTFT_SLOW_SECONDS` |
| `stale_seconds` | number | 旧请求阈值（秒），来自 `MAIN_CHANNEL_REQUEST_STALE_SECONDS` |
| `window_seconds` | number | 取数窗口（秒），来自 `MAIN_CHANNEL_RECENT_WINDOW_SECONDS` |

`data.channels["<channel_id>"]`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `channel_id` | integer | 主站渠道 ID（上游 NewAPI 渠道 id） |
| `state` | string | `active` = 窗口内有请求；`idle` = 窗口内无任何请求（前端整组灰点）；`error` = 该渠道拉取失败（前端显示「—」并悬浮错误原因） |
| `requests` | array | 最多 `MAIN_CHANNEL_RECENT_REQUESTS` 条，**新 → 旧**排序；条目见下 |
| `error` | string \| null | 单渠道拉取失败原因（上游超时 / 限流等）；非 null 时 `state` 为 `error`、`requests` 为空数组 |
| `fetched_at` | string(date-time) | 该渠道数据实际拉取时间（可能来自缓存） |

`data.channels[].requests[]`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `log_id` | integer | 上游日志 ID |
| `created_at` | string(date-time) | 请求发生时间（主站记录） |
| `model_name` | string | 请求的模型名 |
| `ttft_seconds` | number | 首字延迟（秒）。流式取日志 `other.frt`；非流式回退总耗时 `use_time` |
| `total_seconds` | number | 请求总耗时（秒，`use_time`） |
| `is_stream` | boolean | 是否流式请求（判断 `ttft_seconds` 口径用） |
| `age_seconds` | integer | 请求距响应生成时刻的秒数；前端换算「约 N 分钟前」做旧请求说明 |
| `stale` | boolean | 是否超过 `stale_seconds`（默认 900 秒 = 15 分钟）；`true` 时色点画空心圆环 |
| `level` | string | 首字延迟分档：`fast` 绿（< fast_seconds）/ `normal` 橙（两者之间）/ `slow` 红（≥ slow_seconds）；后端按环境阈值算好 |

### 4.4 错误响应（信封 `{"success": false, "code", "message"}`）

| HTTP | code | 场景 |
|---|---|---|
| 400 | `invalid_request` | `channel_ids` 缺失 / 非法 / 超过 100 个 |
| 404 | `admin_site_not_found` | 主站不存在或未配置凭据 |
| 405 | `platform_unsupported` | sub2api 主站（上游无日志接口），同「渠道测试」先例 |

单渠道拉取失败**不**整体报错，失败原因放在该渠道的 `error` 字段。

## 5. 数据链路与保护

- **上游调用**：每渠道一次 `GET {主站}/api/log/?p=1&page_size={N}&type=2&channel={cid}`（消费类日志；**已实测（2026-09）**：渠道过滤参数是 `channel`，`channel_id` 会被上游忽略返回全量；`other.frt` 为首字秒数、`-1000` 是非流式哨兵值，一律回退 `use_time`；`use_time` 整数秒、`created_at` unix 秒。解析兼容 `data` 列表与 `data.items` 两种形状，`other` 兼容 JSON 字符串与 dict）。
- **取数逻辑**：日志按时间倒序返回，取前 N 条后再按窗口过滤（最新 N 条全在窗口外 ⇒ 窗口内无请求 ⇒ `idle`）。
- **缓存（SWR）**：`core/state.py` 注册 `MAIN_CHANNEL_LOGS_CACHE`（TTLCache，内存上界 300s）+ 条目内 `updated_monotonic` 判 60s 新鲜度 + `MAIN_CHANNEL_LOGS_REFRESHING` 防重入后台刷新；照 `monitoring_service` 的 pricing/perf 三件套模式。
- **限速保护**：照 `MAIN_CHANNEL_KEY` 的「预约式限速」模式新注册一组状态（per-base 最小间隔 0.25s、命中 429 写 30s 冷却）；未命中缓存的渠道用 `ThreadPoolExecutor(max_workers=4)` 并发拉取。
- **无数据库变更**、不动调度器、不新增测试文件。

## 8. 验证要点

- 主站监控页新列：切主站、点「刷新请求」；NewAPI 主站有色点，sub2api 主站不出现该列。
- 空态：窗口内无请求的渠道整组灰点；请求不足 10 次缺位灰点；超过 15 分钟的请求呈空心圆环并悬浮「非实时」。
- 数据会实时打主站管理接口（**只读**），首次加载稍慢（60s 内缓存秒开）。
- UI 浅色 + 暗色各过一遍主流程。
- 阈值：改 `.env` 里 5 个变量并重启后，颜色分界 / 窗口 / 旧请求口径随之变化。
